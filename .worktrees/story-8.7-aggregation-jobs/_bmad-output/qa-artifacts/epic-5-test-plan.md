# Epic 5: Gestión de Listings e Integración CRM — Test Plan & Risk Assessment

_Generated by BAD Epic-Start Test Design — 2026-05-16_

## 1. Context & Scope

**Epic Goal:** Las agencias pueden conectar su CRM (Inmovilla) para importar exclusivas automáticamente. El sistema sincroniza y valida listings de forma desacoplada y gestiona el ciclo de vida completo de cada propiedad.

**Functional Requirements Covered:** FR22 (CRM connection), FR23 (webhook sync), FR24 (exclusivity validation), FR25 (duplicate detection), FR26 (withdrawn), FR27 (sold lifecycle), NFR11 (decoupled sync — never block buyer request path), NFR13 (retry on CRM failure).

**Stories:**
- **5.2** Sincronización de Listings via Webhook y Batch Desacoplados (GH #5)
- **5.3** Validación de Exclusividad y Detección de Duplicados (GH #6)
- **5.4** Ciclo de Vida del Listing — Retirada y Vendida (GH #7)

**Tech Stack:** Next.js 15 (web), Supabase Edge Functions (`crm-webhook`), `pg_cron` workers, Drizzle ORM + Supabase PostgreSQL, Realtime WebSockets, Vitest (unit/integration), Playwright (E2E web).

## 2. Risk Assessment

| Risk | Probability | Impact | Priority | Mitigation Strategy |
|------|------------|--------|----------|----------------------|
| **R1:** Webhook processing blocks the buyer swipe feed request path (NFR11 violation) | Medium | Critical | P0 | Verify Edge Function returns `200 OK` immediately and enqueues to DB — never awaits worker. Load test the swipe feed API while webhooks fire concurrently. |
| **R2:** `pg_cron` worker fails silently — listing updates are lost | Medium | High | P1 | Test worker with mock queue entries; verify upsert behavior; test retry logic (3 backoff attempts); verify admin email alert on persistent failure. |
| **R3:** RLS policies incorrectly expose `listings` from Agency A to Agency B queries | Low | Critical | P0 | Dedicated RLS policy tests: query as `agency_admin` of Agency A and assert zero rows from Agency B appear. |
| **R4:** Duplicate detection false positives — valid listings blocked in `pending_review` | Medium | High | P1 | Test catastral reference matching logic with known edge cases (same building, different units). Verify `exclusivity_unverified` fallback when catastro is unreachable. |
| **R5:** `listing.removed`/`listing.updated` Realtime events not emitting after status change | Medium | High | P1 | Integration tests on Realtime channel; verify swipe feed stops serving `withdrawn` listings within 1 request cycle after event. |
| **R6:** Webhook authentication bypass — malicious payloads accepted | Low | Critical | P0 | Unit tests for signature validation in `crm-webhook`; test rejection of unauthenticated payloads (401/403). |
| **R7:** `sold` listings persisting in feed past 72h auto-removal window | Low | Medium | P2 | Test `pg_cron` auto-removal job; assert listings in `sold` state disappear from the feed after the 72h window. |
| **R8:** Batch nightly re-sync triggering duplicate upserts or overwriting manual status changes | Low | Medium | P2 | Verify idempotent upsert logic — listings already `withdrawn` or `sold` must not be reverted to `active` by the batch. |

## 3. Test Strategy

### 3.1 Unit Testing (Backend — Edge Functions & Workers)

- **`crm-webhook` Edge Function:**
  - Test webhook signature validation (accept valid, reject tampered).
  - Test queue enqueue logic — returns `200 OK` synchronously without awaiting worker.
  - Test malformed payload handling (400 response, no DB write).

- **Queue Worker (`pg_cron` processor):**
  - Test upsert logic for new listing (creates `active` record).
  - Test upsert logic for existing listing (updates without duplication).
  - Test retry backoff — mocked third failure triggers admin alert.
  - Test idempotency — running the same queue event twice produces one DB row.

- **Exclusivity Validation Service (Story 5.3):**
  - Test catastral reference uniqueness check — no duplicate → `active`.
  - Test duplicate detected → `pending_review`, admin notified.
  - Test catastro API unreachable → `active` with `exclusivity_unverified: true`.

- **Lifecycle Status Transitions (Story 5.4):**
  - Test `withdrawn` transition: status changes, `listing.removed` event emitted.
  - Test `sold` transition: status changes, `listing.updated` event emitted, 72h timer set.
  - Test post-72h: listing removed from active feed.

### 3.2 Integration Testing (Database & Realtime)

- **RLS Policy Tests:**
  - `agency_admin` of Agency A can only CRUD their own listings.
  - `buyer` role has read-only access to `active` listings only (no `pending_review`, `withdrawn`, `sold`).
  - `platform_admin` can view all listings across agencies.

- **Realtime WebSocket Events:**
  - Subscribe to `listing.*` channel; trigger status change via API; assert event received within 2s.
  - Assert swipe feed API excludes `withdrawn` and `pending_review` listings in the response.

- **Batch Sync (`pg_cron`):**
  - Insert a listing with `last_synced_at` > 24h ago; trigger batch; verify re-sync runs.
  - Verify listings in `withdrawn` or `sold` state are NOT reverted by batch.

### 3.3 Acceptance Testing (ATDD — Story-level Scenarios)

**Story 5.2 — Webhook Sync:**
- **Scenario A:** Agency CRM sends valid webhook → Edge Function returns 200 → within 5min the listing is in the swipe feed.
- **Scenario B:** Edge Function receives invalid signature → 401 returned, nothing written to DB.
- **Scenario C:** Worker fails twice; succeeds on third attempt → listing upserted, admin alert NOT triggered.
- **Scenario D:** Worker fails 3 times → admin receives email alert; listing is NOT in feed.

**Story 5.3 — Exclusivity Validation:**
- **Scenario A:** New listing with unique catastral ref → passes to `active`, visible in feed.
- **Scenario B:** New listing with duplicate catastral ref from another agency → `pending_review`, not in feed, admin alerted.
- **Scenario C:** Catastro API unreachable during import → listing passes to `active` with `exclusivity_unverified: true`.

**Story 5.4 — Lifecycle:**
- **Scenario A:** Admin marks listing as `withdrawn` → disappears from all active buyers' swipe feeds immediately.
- **Scenario B:** Admin marks listing as `sold` → feed shows VENDIDA badge; after simulated 72h → listing absent from feed.
- **Scenario C:** Buyer's match history shows VENDIDA badge for sold listing.

### 3.4 Performance & NFR Testing

- **NFR11 Compliance:** Run `k6` load test: 100 concurrent buyer swipe requests + 20 concurrent webhook deliveries → swipe feed p95 latency must remain ≤1s.
- **NFR13 Retry Validation:** Inject CRM failure; verify 3 exponential backoff retries (1s, 2s, 4s) and admin email alert on final failure.
